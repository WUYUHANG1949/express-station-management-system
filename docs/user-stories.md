# 用户故事与验收标准

> 项目：面向快递驿站的快件收发管理系统
> 作者：吴宇航
> 对应待办：**按功能方式细化需求，每条写作用户故事及验收标准**（截止 2026-10-17）
> 覆盖范围：需求转用户故事、用户故事验收标准、敏捷开发下的用户故事、先写测试与验证方式

---

## 一、这份文档解决什么问题

需求描述的核心要求是：**需求不能只写成功能清单，要写成"谁要做什么、为什么、怎么算做完"**。

原来 `docs/spec.md` 里是 FR-01~FR-30 的功能式描述（输入 / 处理 / 输出），
它回答的是"系统有什么功能"，但回答不了三个问题：

1. 这个功能是**给谁**用的？
2. 做完了**怎么判断真的做完了**？
3. 测试用例**回溯到哪一条需求**？

本文档把 30 条功能需求全部改写成**用户故事 + 验收标准**，
并建立 **功能需求（FR）→ 用户故事（US）→ 验收标准（AC）→ 测试用例（TC）** 的完整追溯链。

## 二、怎么做的（方法四步，可写进开题报告）

| 步骤 | 做什么 | 产出 |
| ---- | ------ | ---- |
| 1 | 从 `spec.md` 取出 30 条功能需求（FR-01~FR-30），按业务域归组 | 7 个 Epic、30 个 Story |
| 2 | 每条需求用康奈尔式句式改写成用户故事：**作为〈角色〉，我想〈做什么〉，以便〈业务价值〉** | 30 条用户故事 |
| 3 | 为每条用户故事写**验收标准**，采用 Given/When/Then（给定—当—则）三段式，保证每条都能判定"通过 / 不通过" | 118 条验收标准 |
| 4 | 把验收标准对应到已有测试用例编号，形成双向追溯；无对应用例的补测 | 30 行追溯矩阵 |

**为什么用 Given/When/Then**：它把"验收标准"拆成前置条件、操作、预期结果三部分，
天然对应一条可执行测试。写成"能正常使用"这种描述无法验收，评审时必然会被追问"怎么算正常"。

**反例 → 正例**

| 不合格 | 问题 | 改后 |
| ------ | ---- | ---- |
| 取件功能要能正常使用 | 无法判定 | 给定快件状态为「在库待取」且取件码与运单号匹配，当员工提交核销时，则状态变为「已取件」，货位占用数减 1 |
| 支持查询 | 无法判定 | 给定额外输入运单号片段，当执行查询时，则列表中只出现包含该片段的记录，且分页总数同步更新 |
| 支持导出台账 | 无法判定 | 给定筛选出 25 条记录，当点击导出时，则下载的 xlsx 含有 1 行表头 + 25 行数据，且列与页面一致 |

## 三、角色定义

| 角色 | 英文 | 说明 | 系统内可见范围 |
| ---- | ---- | ---- | -------------- |
| 收件人 | RECEIVER | 快件的接收方，只关心"我的件到了吗、取件码是多少"；**不是登录主体**，日常查件走免登录自助查询，不需要账号 | 免登录即可查到本人手机号名下（或用取件码、运单号精确定位）的在站快件；如另有管理员创建的 USER 账号，则仅限本人手机号名下的快件 |
| 寄件人 | SENDER | 到驿站寄件的人 | 本驿站寄件单 |
| 驿站员工 | STAFF | 一线作业人员，负责入库、核销、派送、异常处理 | **强制限定为本驿站**，无法越站 |
| 系统管理员 | ADMIN | 维护账号、角色、驿站、货位等基础数据 | 全部驿站 |

> 登录主体只有驿站员工与系统管理员；收件人作为外部服务对象，通过免登录接口获得服务。
> 自助注册已取消，系统内账号（含 USER）一律由管理员在「用户管理」中创建。

## 四、敏捷开发下的用户故事拆分

采用 **Epic（史诗）→ Feature（特性）→ Story（用户故事）→ Task（开发任务）** 四层拆分，
按三个迭代交付，体现敏捷开发下的用户故事组织方式。

### 4.1 四层结构示例（以「取件出库」为例）

```
Epic  E2 快件收寄主流程
 └─ Feature  F2.3 取件核销出库
     ├─ Story  US-13 员工按取件码核销快件
     │   ├─ Task  解析取件码与运单号双重匹配
     │   ├─ Task  校验快件状态是否可取
     │   ├─ Task  计算应缴保管费
     │   ├─ Task  更新状态并释放货位（同一事务）
     │   └─ Task  写取件凭证与轨迹
     ├─ Story  US-14 逾期保管费试算与收取
     └─ Story  US-15 代取与送货上门登记
```

### 4.2 Epic 与迭代规划

| Epic | 名称 | 包含需求 | 包含故事 | 迭代 |
| ---- | ---- | -------- | -------- | ---- |
| E1 | 账号与权限管理 | FR-01~FR-06 | US-01~US-06 | 迭代 1 |
| E2 | 快件收寄主流程 | FR-07~FR-16 | US-07~US-16 | 迭代 2 |
| E3 | 寄件登记 | FR-17~FR-18 | US-17~US-18 | 迭代 2 |
| E4 | 异常件流转 | FR-19~FR-20 | US-19~US-20 | 迭代 2 |
| E5 | 数据统计与台账导出 | FR-21~FR-23 | US-21~US-23 | 迭代 3 |
| E6 | 基础数据管理 | FR-24~FR-25 | US-24~US-25 | 迭代 1 |
| E7 | 通知催取与可视化增强 | FR-26~FR-30 | US-26~US-30 | 迭代 3 |

### 4.3 优先级定义

| 优先级 | 含义 | 判定标准 |
| ------ | ---- | -------- |
| **P0** | 不做系统就跑不通 | 核心业务闭环上的必要环节 |
| **P1** | 不做业务不完整 | 影响正常使用，但有临时替代方案 |
| **P2** | 增强体验 | 不影响主流程，可延后交付 |

### Epic E1 账号与权限管理

#### US-01 用户登录

| 项目 | 内容 |
| ---- | ---- |
| **用户故事** | 作为**系统使用者**，我想用账号密码登录系统，以便进入与我的角色相符的工作界面。 |
| **业务价值** | 一切操作的前提；不同角色看到的菜单与数据范围完全不同。 |
| **关联需求 / 用例** | FR-01 ／ TC-001~TC-005 |
| **优先级 / 迭代** | **P0** ／ 迭代 1 |
| **实现状态** | 已实现（`AuthService.login`、`views/login/index.vue`） |

**验收标准**

- **AC-01-1** 给定账号与密码正确，当提交登录时，则返回 JWT 令牌，页面跳转到首页概览，顶部显示真实姓名与角色。
- **AC-01-2** 给定密码错误，当提交登录时，则提示「用户名或密码错误」，不签发令牌，停留在登录页。
- **AC-01-3** 给定账号被禁用，当提交登录时，则拒绝登录并提示账号已停用。
- **AC-01-4** 给定登录成功，当查看侧边栏时，则菜单项只包含当前角色拥有权限的项（管理员 10 项、员工 9 项、普通用户 3 项）。

#### US-02 账号创建与注册入口关闭

| 项目 | 内容 |
| ---- | ---- |
| **用户故事** | 作为**系统管理员**，我想关闭自助注册、只由我为内部人员创建账号，以便收件人无需注册即可使用自助查询，也避免账号无序增长。 |
| **业务价值** | 账号由管理员统一创建，人员与角色一一对应、可追溯；收件人不占账号也能查到取件码，账号数量不再随收件人增长。 |
| **关联需求 / 用例** | FR-02 ／ TC-006~TC-009 |
| **优先级 / 迭代** | P1 ／ 迭代 1 |
| **实现状态** | 已实现（`AuthController.register` 固定返回业务异常、`/register` 重定向 `/login`、账号由 `views/system/user.vue` 创建） |

**验收标准**

- **AC-02-1** 给定自助注册已关闭，当直接调用 `POST /api/auth/register` 时，则返回 `code = 1001` 与提示「自助注册已关闭：收件人无需账号，请直接使用自助查询；系统内账号请联系管理员创建」，`sys_user` 表记录数不变。
- **AC-02-2** 给定打开登录页，则底部不再出现「立即注册」入口，只提供「收件人查件？免登录自助查询 →」链接；直接访问 `/register` 会被重定向到 `/login`。
- **AC-02-3** 给定以管理员身份进入「用户管理」新增账号并分配角色（ADMIN / STAFF / USER 之一），当提交时，则账号立即创建成功，可立即用该账号登录且菜单与角色相符。
- **AC-02-4** 给定收件人没有任何账号，当打开 `/query` 输入手机号、取件码或运单号时，则照样能查到取件码（自助查询不依赖登录，详见 US-30）。

#### US-03 登录状态维护与退出

| 项目 | 内容 |
| ---- | ---- |
| **用户故事** | 作为**已登录用户**，我想在刷新页面后仍保持登录、并能主动退出，以便不用反复输入密码且能安全离开。 |
| **业务价值** | 令牌在有效期内复用；退出后令牌失效，避免共用电脑时被他人继续操作。 |
| **关联需求 / 用例** | FR-03 ／ TC-010~TC-011 |
| **优先级 / 迭代** | P1 ／ 迭代 1 |
| **实现状态** | 已实现（`request.js` 拦截器、`userStore`） |

**验收标准**

- **AC-03-1** 给定已登录，当按 F5 刷新页面时，则仍停留在当前页面且不跳回登录页。
- **AC-03-2** 给定未登录或令牌已过期，当访问任意受保护页面时，则跳转到登录页并把原地址记为回跳地址。
- **AC-03-3** 给定已登录，当点击右上角退出时，则清除本地令牌并回到登录页；此时再访问受保护页面需重新登录。

### Epic E2 快件收寄主流程

#### US-07 快件入库登记

| 项目 | 内容 |
| ---- | ---- |
| **用户故事** | 作为**驿站员工**，我想把到件登记入库并自动获得取件码，以便通知收件人、并在货架上找到这个件。 |
| **业务价值** | 入库是整个系统的起点；取件码与货位是后续核销、找件的基础。 |
| **关联需求 / 用例** | FR-07 ／ TC-019~TC-025 |
| **优先级 / 迭代** | **P0** ／ 迭代 2 |
| **实现状态** | 已实现（`ParcelService.inStore`、`views/parcel/in.vue`） |

**验收标准**

- **AC-07-1** 给定运单号格式符合所选快递公司规则，当提交入库时，则入库成功，返回 8 位唯一取件码，状态为「在库待取」，并提示可打印小票。
- **AC-07-2** 给定运单号不符合规则（如顺丰未以 SF 开头），当提交时，则拒绝入库并提示该公司的运单号规则与示例。
- **AC-07-3** 给定运单号已存在，当再次入库时，则提示「该运单号已登记，请勿重复入库」，不产生重复数据。
- **AC-07-4** 给定收件人手机号不是 11 位，当提交时，则提示手机号格式不正确。
- **AC-07-5** 给定入库成功，当查该件轨迹时，则至少有一条「入库登记」记录，含操作人、库位与时间。

## 八、验收操作路径

1. 打开系统 <http://localhost:5173>，用 `admin / 123456` 登录
2. 按本文档的 AC 编号逐条验证，例如验证 **AC-13-1**：
   - 进「快件查询」找到一件「在库待取」的快件，记下取件码与货位
   - 去「货位地图」确认该货位有这件
   - 进「取件核销」输入取件码核销
   - 回「货位地图」确认该件已消失、占用数减 1 → 该条验收标准「通过」
3. 其余 AC 同理；P0 的 7 条故事建议优先演示，它们是系统的骨架
