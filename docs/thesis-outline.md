## 2 论文章节大纲

### 第 1 章 绪论（建议 1800 字）

#### 1.1 研究背景与意义（600 字）

写作要点：从电子商务与社区团购规模增长切入，说明快递末端投递量与驿站数量的增长趋势；指出驿站作业的现实痛点，即纸质台账易丢失、凭姓名称呼取件易错领、货位无记录导致找件慢、异常件无处理闭环、经营数据无法统计；阐述本课题的研究意义：以信息化手段实现快件收发全流程数字化，提升取件安全性与作业效率，为驿站经营提供数据支撑。

#### 1.2 国内外研究现状（600 字）

写作要点：介绍国内学者在智能驿站数据库管理、基于 RFID 的校园快递管理、社区团购快递信息管理、智能仓储管理系统等方面的研究成果（对应参考文献）；归纳现有研究的共性不足，如侧重硬件改造投入高、侧重单一环节缺乏收发存闭环、权限与审计设计薄弱；据此引出本课题的定位，即面向中小型驿站的轻量级、全流程、可控权限的软件系统。

#### 1.3 主要研究内容（400 字）

写作要点：列出四项工作。第一，分析驿站收发业务并梳理三类角色权限；第二，设计包含 12 张表的数据库结构与索引策略；第三，实现后端接口服务与前端管理界面；第四，完成功能测试与接口测试。

#### 1.4 论文组织结构（200 字）

写作要点：逐章概述全文七章内容，每章一句话。

### 第 2 章 相关技术介绍（建议 2200 字）

#### 2.1 后端技术选型（700 字）

##### 2.1.1 Spring Boot 3.2.5
写作要点：说明 Spring Boot 的约定优于配置、起步依赖与内嵌容器特性；说明选择 3.2.5 版本的原因，即基于 Spring Framework 6 与 Jakarta EE 9+，要求 JDK 17 及以上，与本文采用的 Java 17 匹配，且为 3.2.x 系列的稳定版本；说明其在项目中的作用，即统一管理依赖、提供 Web 层与事务管理能力。

##### 2.1.2 MyBatis-Plus 3.5.7
写作要点：说明持久层框架的定位；说明选择 MyBatis-Plus 而非 JPA 或原生 MyBatis 的原因，即保留 SQL 可控性的同时提供通用 CRUD、条件构造器、分页插件与逻辑删除能力；结合本系统说明逻辑删除与分页在 `parcel`、`ship_order` 等表上的实际应用。

##### 2.1.3 MySQL 8.0
写作要点：说明关系型数据库在事务一致性上的必要性；说明 8.0 版本在窗口函数、索引与字符集方面的改进；说明本系统统一使用 `utf8mb4` 字符集与 InnoDB 引擎，以支持中文存储与事务性写入。

#### 2.2 前端技术选型（600 字）

##### 2.2.1 Vue 3 与组合式 API
写作要点：说明 Vue 3 的响应式原理与组合式 API 在逻辑复用上的优势；说明其在多角色菜单渲染与表单交互中的适用性。

##### 2.2.2 Vite 与 Element Plus
写作要点：说明 Vite 基于 ESBuild 的冷启动与热更新速度优势，开发服务运行于 5173 端口并通过代理转发 `/api`；说明 Element Plus 提供的表格、表单、分页、树形控件与消息提示组件，与后台管理系统的界面需求高度匹配。

#### 2.3 JWT 认证与 RBAC 权限模型（500 字）

写作要点：说明 JWT 的三段式结构与自包含特性，说明令牌签发、携带与校验流程（有效期 86400 秒，存储于 localStorage 的 `es_token`，请求头 `Authorization: Bearer <token>`）；说明 RBAC 模型的基本要素（用户、角色、权限、用户角色关联、角色权限关联）；说明本系统将权限细分为 `MENU` 与 `BUTTON` 两类，并以 `perm_code` 作为鉴权标识；说明采用 JWT 而非 Session 的动因是前后端分离下无需服务端会话存储。

#### 2.4 本章小结（100 字）

写作要点：概括技术栈整体，强调技术选型与需求特点的匹配性。

##### 3.2.1 角色职责划分

#### 3.3 业务流程分析（800 字）

写作要点：分别描述并绘制四个业务流程的流程图。第一，快件入库流程，重点说明运单号格式校验、唯一性校验、取件码生成与货位自动分配；第二，取件核销流程，重点说明运单号与取件码双重匹配、状态前置校验、四项数据变更在同一事务内完成；第三，寄件受理流程，重点说明寄件单号生成规则与状态流转路径（`PENDING` → `ACCEPTED` → `SHIPPED`，或 `PENDING` → `CANCELLED`）；第四，异常件处理流程，重点说明异常登记时同步快件状态为 `EXCEPTION` 并留痕，处理完成时可传入 `parcelStatus` 同步快件状态。

#### 3.4 功能需求与非功能需求（500 字）

写作要点：以表格形式列出 25 项功能需求（FR-01 至 FR-25），涵盖认证与账号、用户与权限管理、收件登记、取件核销、派送、寄件登记、异常件管理、快件查询、数据统计与导出、驿站与货位管理；从性能、安全性、可用性、可维护性、兼容性五个方面归纳非功能需求，其中安全性重点说明 BCrypt 密码加密、JWT 认证与接口鉴权。

## 3 各章节可直接使用的写作素材

### 3.1 技术选型理由

**（1）为什么选择 Spring Boot 3.2.5**

本系统后端选择 Spring Boot 3.2.5 作为基础框架，主要基于三方面考虑。其一，Spring Boot 以"约定优于配置"为设计理念，通过起步依赖与自动配置大幅减少了传统 Spring 应用所需的 XML 配置与依赖管理工作，使开发者能够将精力集中于业务逻辑本身，这对开发周期有限的毕业设计项目尤为重要。其二，Spring Boot 内嵌 Tomcat 容器，应用可直接以可执行 JAR 形式独立运行并监听 8080 端口，无需额外部署 Web 容器，简化了开发与演示环境的搭建。其三，Spring Boot 3.2.5 基于 Spring Framework 6 与 Jakarta EE 9+ 构建，要求 JDK 17 及以上版本，与本系统采用的 Java 17 完全匹配，同时在事务管理、参数校验、统一异常处理等方面提供了成熟的支撑能力。相较之下，传统的 SSM 框架需要手工整合 Spring、Spring MVC 与 MyBatis 并维护大量配置文件，开发效率较低；而 Node.js 或 Python 技术栈虽然上手较快，但在企业级事务管理与生态成熟度方面不及 Spring 生态，与国内外物流信息系统的技术主流也存在差距，因此最终选择 Spring Boot 3.2.5。

**（2）为什么选择 MyBatis-Plus 3.5.7**

持久层框架在 MyBatis-Plus、原生 MyBatis 与 Spring Data JPA 之间进行了比较。原生 MyBatis 的 SQL 完全可控，但需要为每张表手工编写基础增删改查语句，在拥有 12 张表的系统中会产生大量重复代码；Spring Data JPA 以对象关系映射为中心，开发效率较高，但对于"按驿站与状态统计快件数量""按日期分组统计出入库趋势"等复杂聚合查询，其表达能力不如手写 SQL 直观。MyBatis-Plus 3.5.7 在保留 MyBatis SQL 可控性优势的基础上，提供了通用 CRUD 接口、条件构造器、分页插件与逻辑删除等增强能力。本系统中，分页插件直接支撑了 `pageNum`、`pageSize` 参数到数据库分页的转换，返回契约要求的 `total`、`pages`、`pageNum`、`pageSize`、`list` 结构；逻辑删除能力使 `sys_user`、`parcel`、`ship_order` 三张表在查询时自动附加 `deleted = 0` 条件、在删除时自动改写为更新语句，避免了在业务代码中重复编写过滤逻辑。因此选择 MyBatis-Plus 3.5.7 作为持久层框架。

**（3）为什么选择 MySQL 8.0**

本系统涉及快件入库、取件核销、寄件受理等业务操作，其中的取件核销需要同时更新快件状态、写入取件记录、写入操作轨迹并释放货位占用，对事务的原子性有明确要求，因此选择支持事务与行级锁的关系型数据库。MySQL 8.0 是当前应用最广泛的开源关系型数据库之一，在 8.0 版本中对字符集、索引与执行计划等方面均有改进，能够满足本系统对中文存储与查询性能的需求。系统统一采用 `utf8mb4` 字符集与 `utf8mb4_general_ci` 排序规则，保证快递公司名称、收件人姓名、地址等中文字段的正确存储与检索；统一采用 InnoDB 存储引擎，以获得事务支持、行级锁与崩溃恢复能力。此外，MySQL 8.0 的安装配置简便、社区资料丰富，便于在 Windows 11 环境下快速搭建测试数据库并执行结构脚本与初始化数据脚本。

**（4）为什么选择 Vue 3 + Vite + Element Plus**

前端框架在 Vue 3 与 React 之间进行了比较。Vue 3 具有上手曲线平缓、模板语法直观、中文文档完善的特点，其组合式 API 便于将"权限判断""分页查询""表单校验"等逻辑抽取为可复用的组合函数，与本系统多页面复用相同查询与权限逻辑的场景契合。构建工具选择 Vite，其基于原生 ES 模块的开发服务器具备快速冷启动与热更新能力，前端开发服务运行于 5173 端口，并通过代理配置将 `/api` 前缀的请求转发至后端 `http://localhost:8080`，从而在开发阶段避免跨域问题。UI 组件库选择 Element Plus，其提供的表格、表单、分页、树形控件、日期选择器与消息提示组件可直接满足后台管理系统的界面需求，其中表格组件支持自定义列与操作按钮插槽，便于通过 `v-perm` 指令控制按钮显隐；树形控件可直接渲染由 `/api/auth/menus` 返回的菜单树。整体方案在开发效率、界面规范性与学习成本之间取得了较好的平衡。

**（5）为什么选择 JWT 作为认证方案**

本系统采用前后端分离架构，前端为单页应用，后端仅提供无状态接口服务。若采用基于 Session 的传统认证方式，服务端需要保存会话状态，在接口请求中依赖 Cookie 传递会话标识，不仅需要处理跨域场景下的 Cookie 策略，还需要考虑会话存储与服务器扩展问题。JWT 是一种自包含的令牌，其载荷中携带用户标识与基础信息，服务端无须保存会话即可完成身份校验，与前后端分离架构天然契合。本系统中，登录成功后返回 `token`、`tokenType` 与 `expiresIn`（86400 秒），前端将令牌存储于 localStorage 的 `es_token`，后续请求在请求头中携带 `Authorization: Bearer <token>`，后端通过拦截器统一校验令牌的签名与有效期。当令牌缺失、被篡改或过期时，接口返回 `code = 401`、`message = 登录已过期，请重新登录`，前端据此清除令牌并跳转登录页。需要注意的是，JWT 一经签发在有效期内无法主动作废，因此系统将令牌有效期设置为 24 小时，并通过退出登录时清除前端令牌的方式完成登出语义。

### 3.2 系统架构描述段落

本系统采用前后端分离的 B/S 架构，前端与后端作为两个独立工程分别开发、构建与部署，通过网络接口进行数据交换。前端基于 Vue 3 与 Vite 构建单页应用，开发服务运行于 5173 端口；后端基于 Spring Boot 3.2.5 构建，以可执行 JAR 形式独立运行并监听 8080 端口，对外提供 RESTful 风格的 JSON 接口，全部业务接口统一使用 `/api` 前缀，例如认证接口 `/api/auth/login`、收件登记接口 `/api/parcels/in-store`、取件核销接口 `/api/parcels/pickup`。开发阶段，前端通过 Vite 的代理配置将 `/api` 前缀的请求转发至 `http://localhost:8080`，从而在不修改后端跨域配置的前提下完成联调。

前后端之间的数据交换遵循统一的接口契约。所有接口（文件下载接口除外）均返回统一响应体 `{ code, message, data }`，其中 `code = 200` 表示成功，`code = 400` 表示参数校验不通过，`code = 401` 表示未登录或令牌失效，`code = 403` 表示已登录但无操作权限，`code = 404` 表示资源不存在，`code = 500` 表示服务器内部错误，`code = 1001` 表示业务异常且 `message` 为可直接展示给用户的中文提示。分页接口的 `data` 固定包含 `total`、`pages`、`pageNum`、`pageSize` 与 `list` 五个字段，请求统一使用 `pageNum` 与 `pageSize` 两个查询参数。统一的响应结构与错误码体系使前端能够以一致的方式处理成功与异常分支，也使接口测试具备明确的断言依据。

后端内部采用 Controller、Service、Mapper 三层结构。Controller 层负责接收请求、完成参数绑定与基础校验，并将 Service 层返回的结果封装为统一响应体；Service 层承载业务规则与事务边界，例如取件核销的全部数据变更均在同一事务内完成，收件登记中货位容量的判断与占用更新亦在此层实现；Mapper 层基于 MyBatis-Plus 完成数据访问，通过条件构造器动态拼接查询条件。身份认证与权限校验作为横切关注点，由令牌拦截器与权限校验组件统一处理，避免在每个业务方法中重复编写鉴权代码；异常处理则由全局异常处理器集中接管，将业务异常与系统异常分别转换为契约约定的业务码与通用错误提示，避免向前端暴露堆栈信息与数据库结构。

### 3.3 数据库设计描述段落

系统数据库名为 `express_station`，共设计 12 张数据表，按功能划分为系统权限表与业务表两组。系统权限表共 5 张，包括用户表 `sys_user`、角色表 `sys_role`、用户角色关联表 `sys_user_role`、权限表 `sys_permission` 与角色权限关联表 `sys_role_permission`，它们共同构成基于角色的访问控制模型。业务表共 7 张，包括驿站表 `station`、货架库位表 `shelf`、快件表 `parcel`、快件轨迹表 `parcel_trace`、取件记录表 `pickup_record`、寄件登记表 `ship_order` 与异常件记录表 `exception_record`。所有表统一使用 `BIGINT` 类型的自增主键 `id`，统一使用 `utf8mb4` 字符集与 InnoDB 存储引擎。

表结构设计在满足第三范式的基础上对高频查询场景做了适度冗余。快件表 `parcel` 作为核心业务表，记录运单号 `waybill_no`、所在驿站 `station_id`、存放库位 `shelf_id`、快递公司 `express_company`、快件类型 `parcel_type`、收件人信息、取件码 `pickup_code`、重量与运费、状态 `status`、入库时间 `in_time`、取件时间 `pickup_time`、免费保管天数 `overdue_days`、逾期保管费 `storage_fee` 与入库操作员 `operator_id` 等字段。轨迹表 `parcel_trace` 除关联字段 `parcel_id` 与 `operator_id` 外，额外冗余了运单号 `waybill_no` 与操作人姓名 `operator_name`，其目的在于既支持按运单号直接检索轨迹、避免多表连接，又固化操作发生时的操作人姓名快照，保证历史轨迹不因用户表数据变更而被改写。取件记录表 `pickup_record` 采用相同的冗余策略，同时固化核销时使用的取件码 `pickup_code`，形成不可篡改的凭据留痕。

索引设计依据实际查询条件确定。其中 `uk_parcel_waybill` 为运单号唯一索引，既承担收件登记查重、详情查询与核销匹配的检索职责，又从数据库层面杜绝并发场景下的重复入库；`idx_parcel_station_status` 为 `(station_id, status)` 复合索引，服务按驿站与状态筛选快件、统计在库量与异常量等高频场景，其列顺序遵循最左前缀原则，使 `station_id` 既能用于联合过滤，也能独立支撑按驿站的聚合统计；`idx_parcel_pickup_code` 为取件码普通索引，是窗口取件检索的关键路径。状态字段统一采用字符串枚举而非数字编码，例如快件状态取值为 `IN_STORE`、`PICKED_UP`、`DELIVERING`、`EXCEPTION`、`RETURNED`，寄件单状态取值为 `PENDING`、`ACCEPTED`、`SHIPPED`、`CANCELLED`，使数据记录具备自解释能力，并与接口契约中返回的枚举值保持完全一致。对于用户表、快件表与寄件单表，系统采用逻辑删除字段 `deleted`（0 未删除、1 已删除）替代物理删除，以保留历史台账与操作追溯能力。

### 3.4 核心功能实现描述段落

**（1）收件登记实现**

收件登记是全部业务数据的入口，其接口为 `POST /api/parcels/in-store`。员工提交运单号、驿站、快递公司、快件类型、收件人姓名与手机号、重量、代收运费、货位、免费保管天数与备注等信息后，后端按以下顺序处理：首先依据快递公司对应的正则规则校验运单号的格式，格式不符时返回 `code = 1001`、`message = 运单号格式不正确，请核对快递公司`；随后查询 `parcel` 表判断运单号是否已存在，重复时返回 `code = 1001`、`message = 该运单号已登记，请勿重复入库`；接着校验收件人手机号为 11 位手机号；校验通过后由系统生成 8 位数字取件码。存放货位的确定分两种情况：若请求中携带 `shelfId`，则校验该货位属于目标驿站、状态为可用且 `used_count` 小于 `capacity`，容量不足时返回 `code = 1001`、`message = 该货位已满，请选择其他货位`；若未携带 `shelfId`，则由系统在该驿站 `status = 1` 且剩余容量大于 0 的货位中选取剩余容量最大者自动分配。最后，系统写入 `parcel` 记录并设置状态为 `IN_STORE`、`in_time` 为当前时间、`operator_id` 为当前登录员工，将对应 `shelf.used_count` 加 1，并写入一条 `operate_type = 'IN_STORE'` 的 `parcel_trace` 轨迹记录，从而保证快件主记录、货位计数与操作轨迹三者同步生成。

**（2）取件核销的事务一致性实现**

取件核销是系统内一致性要求最高的操作，其接口为 `POST /api/parcels/pickup`。该操作首先要求运单号与取件码同时匹配，任一项不一致即返回 `code = 1001`、`message = 取件码不正确，请核对`，这一双重校验设计有效防止了错领与冒领；匹配成功后校验快件状态必须为 `IN_STORE`，对于已取件、派送中、异常或已退回的快件，返回 `code = 1001`、`message = 该快件当前状态不可取件`。在核销执行前，系统可调用 `GET /api/parcels/{id}/overdue-fee` 试算在库天数与逾期保管费，其返回值包含 `storageDays`、`overdueDays` 与 `overdueFee` 三个字段。

核销过程涉及四张表的数据变更：更新 `parcel` 表的状态为 `PICKED_UP`、写入 `pickup_time` 与实收 `storage_fee`；向 `pickup_record` 表插入取件记录，记录取件方式 `pickup_type`、核验方式 `verify_type`、实际取件人、核销操作员与取件时间；向 `parcel_trace` 表插入一条 `operate_type = 'PICKUP'` 的轨迹；将对应 `shelf` 记录的 `used_count` 减 1 以释放货位占用。上述四项操作被置于同一数据库事务中，任一步骤抛出异常都会触发整体回滚，从而避免出现"快件状态已变更为已取件但取件记录缺失""取件记录已写入但货位占用未释放"等中间态数据。在并发控制方面，更新快件状态时以 `id` 与 `status = 'IN_STORE'` 作为联合条件，若受影响行数为 0 则说明该快件已被其他操作核销，事务回滚并返回状态不允许取件的提示，从而保证同一票快件不会被重复核销。

**（3）权限控制实现**

系统的权限控制建立在 RBAC 模型之上，由 `sys_user`、`sys_role`、`sys_user_role`、`sys_permission`、`sys_role_permission` 五张表共同支撑，用户与角色、角色与权限均为多对多关系。系统预置三类角色：`ADMIN` 系统管理员拥有全部权限，`STAFF` 驿站员工拥有除系统管理与删除操作之外的业务权限，`USER` 普通用户仅拥有首页概览、快件查询与个人中心三项权限。权限记录通过 `perm_type` 字段区分为 `MENU` 与 `BUTTON` 两类：`MENU` 类型的权限带有前端路由地址 `path` 与图标 `icon`，用于渲染侧边菜单；`BUTTON` 类型的权限以权限标识 `perm_code` 表示，例如 `parcel:export`、`system:user:reset`，用于控制页面内操作按钮的可用性。

权限控制在前端与后端两个层面协同实现。后端层面，令牌拦截器解析请求头中的 JWT 并注入当前用户上下文，权限校验组件依据接口所需的权限标识判断当前用户的权限集合是否包含该项，校验不通过时返回 `code = 403`、`message = 无操作权限，请联系管理员`，未携带令牌或令牌无效时返回 `code = 401`、`message = 登录已过期，请重新登录`。前端层面，登录成功后保存后端返回的 `permissions` 数组，侧边菜单依据 `GET /api/auth/menus` 的菜单树动态渲染，页面内的操作按钮通过自定义指令 `v-perm="'parcel:export'"` 或方法 `hasPerm('parcel:export')` 控制显隐。这种"前端隐藏 + 后端拦截"的双重控制既保证了界面的简洁性，又确保了即使绕过前端直接调用接口也无法越权操作。此外，系统还实现了数据层面的权限隔离：员工的操作范围限定于所属驿站，接口在处理时按 `station_id` 过滤；普通用户查询快件时，后端强制以当前登录用户的 `phone` 字段过滤 `receiver_phone`，即使请求参数中携带他人手机号也不会返回他人数据。

## 5 答辩准备：15 个问题与回答要点

### 问题 1：为什么使用 JWT 而不是 Session？

1. 本系统采用前后端分离架构，前端为运行于 5173 端口的单页应用，后端为仅提供接口的 8080 端口服务。Session 机制要求服务端保存会话状态并依赖 Cookie 传递会话标识，在跨域场景下需额外处理 Cookie 属性与跨域策略。
2. JWT 是自包含令牌，载荷中携带用户标识，服务端无须存储会话即可完成校验，与无状态接口服务的设计目标一致。
3. 本系统登录成功后返回 `token`、`tokenType = Bearer` 与 `expiresIn = 86400`，前端将令牌存放于 localStorage 的 `es_token`，请求头统一携带 `Authorization: Bearer <token>`，后端通过拦截器集中校验签名与有效期。
4. 令牌失效场景（缺失、被篡改、过期）统一返回 `code = 401` 与"登录已过期，请重新登录"，前端清除令牌并跳转登录页。
5. 局限在于 JWT 在有效期内无法主动作废，因此将有效期设为 24 小时，并以退出登录时清除前端令牌的方式完成登出语义；若后续需要强制下线能力，可引入令牌黑名单机制。

### 问题 2：取件核销怎么保证事务一致性？

1. 取件核销在 `POST /api/parcels/pickup` 接口中实现，涉及四张表的变更：`parcel` 状态更新为 `PICKED_UP` 并写入 `pickup_time`、`storage_fee`；`pickup_record` 插入取件记录；`parcel_trace` 插入 `operate_type = 'PICKUP'` 的轨迹；`shelf.used_count` 减 1 释放货位。
2. 四项操作由 Service 层的同一事务包裹，任一步骤抛出异常即整体回滚，不会留下"状态已改而记录未写"或"记录已写而货位未释放"的中间态。
3. 前置校验在事务内执行：先要求运单号与取件码同时匹配（不匹配返回 `code = 1001`、"取件码不正确，请核对"），再校验快件状态必须为 `IN_STORE`（否则返回"该快件当前状态不可取件"）。
4. 并发场景下采用条件更新：更新快件时以 `id = ? AND status = 'IN_STORE'` 为条件，受影响行数为 0 即说明已被他人核销，事务回滚，保证同一票快件不被重复核销。
5. 货位计数使用基于当前值的增减操作而非读改写，避免丢失更新。

### 问题 3：权限是怎么做到按钮级的？

1. 权限数据存储于 `sys_permission` 表，通过 `perm_type` 区分 `MENU` 与 `BUTTON` 两类；`BUTTON` 类型权限以 `perm_code` 标识，例如 `parcel:export`、`parcel:delete`、`system:user:reset`。
2. 登录成功后，接口返回的 `userInfo.permissions` 包含当前用户拥有的全部 `perm_code`，前端将其保存。
3. 菜单由 `GET /api/auth/menus` 返回的菜单树动态渲染，仅返回用户拥有权限的 `MENU` 节点，通过 `parent_id` 组织层级。
4. 页面内按钮通过自定义指令 `v-perm="'parcel:export'"` 或方法 `hasPerm('parcel:export')` 控制显隐，无权限时按钮不渲染。
5. 后端对每个受保护接口校验所需权限，未授权返回 `code = 403`、"无操作权限，请联系管理员"，因此即使绕过前端直接调用接口也无法越权，形成"前端隐藏 + 后端拦截"的双重控制。

### 问题 4：运单号正则校验怎么设计的？

1. 运单号由各快递公司自行定义，格式不统一，因此采用按快递公司分组维护正则规则的方式，在收件登记时依据 `expressCompany` 选择对应规则。
2. 校验规则在服务端执行，校验不通过时返回 `code = 1001` 与"运单号格式不正确，请核对快递公司"，提示语与接口契约第 9 节完全一致。
3. `parcel.waybill_no` 字段定义为 `VARCHAR(40)`，由唯一索引 `uk_parcel_waybill` 承担唯一性约束，正则校验负责格式，唯一索引负责重复，二者职责分离。
4. 正则只做基本形态约束（如长度区间、允许的字符集合、常见前缀），不追求覆盖所有快递公司的全部单号规则，以避免误拒绝合法运单；对确实无法匹配的少量运单，可通过扩展规则表解决。
5. 该设计属于"宽进严查"策略：格式校验拦截明显错误的输入，真正的重复与合法性最终由数据库唯一索引保证。

### 问题 5：数据库索引怎么考虑的？

1. 索引依据实际查询条件设计，覆盖三类场景：唯一性约束、高频筛选与排序、范围统计。
2. `uk_parcel_waybill` 为运单号唯一索引，既服务查重、详情查询与核销匹配，又从数据库层杜绝并发重复入库。
3. `idx_parcel_station_status` 为 `(station_id, status)` 复合索引，服务按驿站与状态筛选快件、统计在库量与异常量等场景，列顺序遵循最左前缀原则，`station_id` 作为最左列既能参与联合过滤，也能独立支持按驿站的聚合统计。
4. `idx_parcel_pickup_code` 为取件码索引，是窗口取件检索的关键路径；取件码未设为唯一索引，因为其按驿站生成并可能复用，核销时依靠运单号与取件码双重匹配加状态校验确定唯一对象。
5. 其他索引包括 `idx_parcel_receiver_phone`（支撑普通用户按本人手机号过滤）、`idx_parcel_in_time`（支撑时间区间与趋势统计）、`idx_trace_parcel`、`idx_pickup_time`、`idx_ship_status`、`idx_exception_status` 等。
6. 索引数量受控：`parcel` 表共 1 个主键、1 个唯一索引与 4 个普通索引，新增索引前须确认存在真实查询场景，避免影响入库与核销的写入性能。

### 问题 6：系统有什么创新点或特色？

1. 取件凭据的"双码分离"设计：将快递公司的运单号与系统生成的 8 位数字取件码分离存储并分别建索引，取件时要求两者同时匹配，兼顾了面向收件人的可口头传递性与核销的安全性。
2. 货位的量化管理：不仅记录快件存放库位，还维护 `shelf.used_count`，支持在收件登记时自动分配剩余容量最大的可用货位，并在核销、删除、更换货位等场景同步维护计数，使货位占用可量化、可分析。
3. 逾期保管费的试算与固化分离：试算接口实时计算 `storageDays` 与 `overdueFee`，实际收取金额在核销时写入 `parcel.storage_fee` 与 `pickup_record.storage_fee`，做到过程量实时计算、结果量持久固化。
4. 异常件闭环管理：异常登记时同步将快件状态置为 `EXCEPTION` 并写入轨迹，处理时可指定 `parcelStatus` 同步快件状态，形成"发现—登记—处理—状态同步"的闭环。
5. 菜单级与按钮级双级权限：权限表通过 `perm_type` 区分 `MENU` 与 `BUTTON`，前后端协同实现界面隐藏与接口拦截的双重控制，并实现按驿站与按手机号的数据权限隔离。

### 问题 7：为什么用逻辑删除而不是物理删除？

1. 快件与寄件单属于业务凭证，物理删除会导致 `parcel_trace`、`pickup_record`、`exception_record` 中以 `parcel_id` 关联的明细记录成为孤立数据，无法还原当日台账。
2. 系统需要保留"某票快件被登记后又删除"的事实，以满足对账差异排查与责任追溯需要。
3. `sys_user`、`parcel`、`ship_order` 三张表设置 `deleted` 字段（`TINYINT`，0 未删除、1 已删除），删除接口执行更新而非删除语句。
4. MyBatis-Plus 提供逻辑删除能力，查询时自动附加 `deleted = 0`，删除时自动改写为更新语句，业务代码无需重复编写过滤逻辑。
5. 配套约束：所有业务查询与统计必须携带 `deleted = 0`；删除快件时需同步释放货位占用，保证 `shelf.used_count` 准确；由于 `uk_parcel_waybill` 作用于全表，已逻辑删除的运单号仍占用唯一约束，若需重新入库应恢复原记录或改用包含 `deleted` 的组合唯一索引。

### 问题 8：状态字段为什么用字符串枚举而不是数字？

1. 可读性高：直接查看数据库时 `status = 'IN_STORE'` 语义自明，而数字编码需反复对照字典，排障与人工核对数据的效率显著提升。
2. 避免编码错位：数字编码需要在代码、数据字典与前端三处维护同一套映射，任何一处调整都可能产生不一致；字符串枚举以常量集中定义，前端直接使用相同字面值进行条件渲染。
3. 与接口契约天然一致：`docs/api-contract.md` 中定义的枚举即数据库存储值，接口返回的 `status` 与 `statusName` 一一对应，无需额外的编码转换层。
4. 便于扩展：新增状态只需扩展枚举取值，不必重新规划数字区间。
5. 代价评估：存储空间略大于整型、比较效率略低，但状态字段取值集合极小，`VARCHAR(20)` 在 `utf8mb4` 下的空间开销有限，且系统数据量级为万级，性能差异可以忽略；同时通过应用层枚举约束所有写入路径，非法取值返回 `code = 400`。

### 问题 9：取件码与运单号为什么要分离？

1. 运单号由快递公司生成，包含字母与数字组合、长度可达数十字符，形态不统一，不适合作为面向收件人的口头凭据。
2. 取件码由系统生成，固定为 8 位数字，便于收件人在电话或取件现场准确报出，显著降低沟通成本与误听概率。
3. 二者分离后，取件码的生成规则、有效期与复用策略可独立演进，不影响运单号这一外部标识的存储与校验逻辑。
4. 核销时要求 `waybillNo` 与 `pickupCode` 同时匹配，构成双重凭据，任一不符即返回"取件码不正确，请核对"，有效降低错领与冒领风险。
5. 存储与索引层面，两字段在 `parcel` 表分列存储，并分别建立 `uk_parcel_waybill` 与 `idx_parcel_pickup_code`，各自服务不同维度的查询需求。

### 问题 10：高并发下取件码如何保证唯一？

1. 取件码在同一驿站同一时刻不重复即可满足业务需要，`pickup_code` 因此设计为普通索引而非唯一索引，避免唯一约束限制取件码的分配空间。
2. 生成环节：取件码在收件登记时生成，采用固定 8 位数字空间，生成后校验当前驿站是否存在状态为 `IN_STORE` 的同码快件，存在则重新生成，形成小范围重试机制。
3. 核销环节的最终唯一性不依赖取件码本身，而由"运单号 + 取件码 + 状态为 `IN_STORE`"三重条件共同确定目标快件，从业务语义上保证核销对象唯一。
4. 数据完整性由数据库约束兜底：`uk_parcel_waybill` 防止并发重复入库，条件更新（`status = 'IN_STORE'` 作为更新条件）防止并发重复核销。
5. 若后续驿站规模扩大，可将生成策略调整为"驿站编码前缀 + 自增序列"或引入分布式序列，以进一步降低碰撞概率。

### 问题 11：前后端分离的跨域问题怎么解决？

1. 开发阶段通过 Vite 的代理配置解决：前端开发服务运行于 5173 端口，代理将 `/api` 前缀的请求转发至 `http://localhost:8080`，浏览器视角下请求与页面同源，因而不触发跨域限制。
2. 后端接口统一使用 `/api` 前缀，前后端共用同一路径约定，便于代理规则的集中配置。
3. 生产部署时前端构建产物作为静态资源由 Web 服务器托管，可通过同一域名下的反向代理将 `/api` 转发至后端服务，从而在部署阶段同样避免跨域。
4. 认证信息通过请求头 `Authorization: Bearer <token>` 携带而非 Cookie，不涉及跨域 Cookie 属性与凭证模式配置，进一步简化了跨域处理。

### 问题 12：为什么选择 MyBatis-Plus 而不是原生 MyBatis 或 JPA？

1. 原生 MyBatis 的 SQL 完全可控，但 12 张表的基础增删改查需要大量重复编写，开发效率低。
2. Spring Data JPA 的开发效率较高，但"按驿站与状态统计数量""按日期分组统计出入库趋势"等聚合查询的表达能力不如手写 SQL 直观。
3. MyBatis-Plus 3.5.7 在保留 SQL 可控性的同时，提供通用 CRUD、条件构造器、分页插件与逻辑删除能力。
4. 本系统的分页接口需要返回 `total`、`pages`、`pageNum`、`pageSize`、`list` 结构，MyBatis-Plus 的分页插件直接支撑了该契约的实现。
5. 逻辑删除能力使 `sys_user`、`parcel`、`ship_order` 在查询时自动附加 `deleted = 0`、删除时自动改写为更新，避免了业务代码中的重复判断。

### 问题 13：系统还有哪些不足与改进方向？

1. 未对接快递公司开放平台，运单号由员工人工录入，存在录入错误与效率损失；后续可对接运单查询接口实现自动同步。
2. 未接入短信或微信通知能力，取件码依赖员工电话通知；后续可增加消息推送模块。
3. 仅提供 Web 端，未实现移动端与扫码枪支持；后续可开发移动端并支持扫码录入运单号与取件码。
4. 统计维度较基础，缺少按员工绩效、按时段分布的分析；后续可扩展统计模型。
5. 逻辑删除与全表唯一索引在运单号复用场景下存在约束冲突，需要人工恢复记录或调整索引结构。
6. 未引入缓存与消息队列，在高并发取件场景下数据库压力较大；后续可引入缓存与其他中间件优化（本期未使用）。

### 问题 14：如何防止越权查询他人快件？

1. 普通用户（`USER`）仅拥有 `dashboard`、`parcel:list`、`profile` 三项权限，无法访问收件登记、取件核销、寄件管理、异常件管理与系统管理功能。
2. 调用 `GET /api/parcels/page` 时，后端强制以当前登录用户的手机号过滤 `receiver_phone`，即使请求参数中传入他人手机号也不会返回他人数据。
3. 该过滤在服务端实现，不依赖前端传参，因此通过 Postman 等工具直接构造请求同样无法绕过。
4. 员工（`STAFF`）的数据范围限定于所属驿站，接口按 `station_id` 过滤；系统管理员不受驿站限制。
5. 接口层面的权限校验由令牌拦截器与权限组件统一完成，未授权返回 `code = 403`、"无操作权限，请联系管理员"。

### 问题 15：测试用例是如何设计的？

1. 依据《软件需求规格说明书》的 25 项功能需求与《前后端接口契约》的接口清单设计用例，并建立需求与用例的覆盖矩阵，保证每项功能需求至少被一条用例覆盖。
2. 方法上综合运用等价类划分、边界值分析与错误推测：登录与注册按合法与非法输入划分等价类；分页参数、密码长度按边界值设计；重复运单号、重复核销、并发操作按错误推测设计。
3. 用例覆盖三类角色的权限隔离，包括普通用户访问系统管理接口返回 `code = 403`、员工访问用户管理接口返回 `code = 403`、未携带令牌返回 `code = 401`。
4. 预期结果写得具体可验证：给出预期提示语原文、预期业务码与预期数据库变化，例如核销后 `parcel.status = 'PICKED_UP'`、`pickup_record` 新增 1 行、`parcel_trace` 新增 `operate_type = 'PICKUP'` 轨迹、`shelf.used_count` 减 1。
5. 统计上共设计功能测试用例 73 条、接口测试用例 46 条；"实际结果"列由测试人员执行后人工复核确认，失败用例登记缺陷编号并纳入回归测试范围。
