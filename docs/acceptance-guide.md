> 用途：给导师现场演示时，按本文档逐条点、逐条勾，每一条都能当场判定"通过 / 不通过"。
> 配套文档：`docs/user-stories.md`（验收标准原文）、`docs/test-cases.md`（完整用例）。
> 系统地址：<http://localhost:5173>　账号：`admin / 123456`、`staff01 / 123456`、`user01 / 123456`

## 一、通用四步法

任何一条验收标准都是"给定 — 当 — 则"三段结构，验收就是把它变成三个动作：

| 步骤 | 做什么 | 对应 AC 的哪一段 |
| ---- | ------ | ---------------- |
| 1 | 确认前置条件成立（有什么数据、谁登录） | **给定** |
| 2 | 在系统里执行操作 | **当** |
| 3 | 看结果是否与预期完全一致 | **则** |
| 4 | 在记录表里勾"通过 / 不通过" | 判定 |

**判定原则**：预期写了什么就核什么，数量、文案、状态、关联数据都要对得上。
只"页面没报错"不能算通过。

## 二、实例 1：收件登记（AC-07-1、AC-07-2、AC-08-1）

**验收目的**：证明入库能校验运单号、自动生成取件码、自动分配货位。

### 前置条件
- 用 `admin / 123456` 登录
- 当前在库快件 **16** 件（可在「首页概览 → 在库快件」核对）

### 操作步骤

| 步 | 操作 | 位置 |
| -- | ---- | ---- |
| 1 | 点左侧「快件管理 → 收件登记」 | 侧边栏 |
| 2 | 运单号填 `SF1234567890123`、收件人填任意姓名、手机号填 `13900000099`、快递公司选「顺丰速运」 | 表单 |
| 3 | 点「登记入库」 | 表单底部 |

### 预期结果

- **弹出成功提示**，文案含「入库成功，取件码：XXXXXXXX」（8 位数字）
- 自动分配了一个货位，提示里带库位编号（如 `B-01-01`）
- 「首页概览 → 在库快件」由 **16 变成 17**
- 新件的状态为「在库待取」

### 再验一条反例（AC-07-2）

| 步 | 操作 | 预期 |
| -- | ---- | ---- |
| 1 | 运单号填 `SF123`（位数不足） | 提交被拒绝 |
| 2 | 看提示文案 | 「顺丰速运运单号以 SF 开头，后接 12~15 位数字，例如 SF1234567890123」 |

> **记得把刚才那个取件码记下来**，实例 2 要用。

**答辩话术**：*"运单号按快递公司分别做正则校验，不合规在提交前就拦掉；取件码是 8 位数字且全局唯一；货位按剩余容量自动挑最大的那个，避免某个格先被占满。"*

## 三、实例 2：取件核销闭环 + 货位一致性（AC-13-1、AC-13-5）
### ⭐ 这是最该演示的一个

**验收目的**：证明核销能一次性把"状态、货位、凭证"三件事同时改对——这是本系统的核心难点。

### 前置条件
- 用**实例 1 刚入库的取件码**（8 位数字）
- 先打开「货位地图」，找到那个货位，记住它的「已用 / 剩余」数字

### 操作步骤

| 步 | 操作 | 位置 |
| -- | ---- | ---- |
| 1 | 点「货位地图」，找到实例 1 提示的库位（如 `B-01-01`），记下 **已用数** | 侧边栏 → 货位地图 |
| 2 | 点「快件管理 → 取件核销」 | 侧边栏 |
| 3 | 输入实例 1 的取件码，按回车 | 顶部查询框 |
| 4 | 下方出现匹配卡片，点卡片选中 | 匹配结果区 |
| 5 | 取件方式选「本人自取」，核验方式选「取件码核验」 | 核销表单 |
| 6 | 点「确认核销」 | 表单底部 |
| 7 | **回到「货位地图」，再看同一个库位** | 侧边栏 |

### 预期结果（逐条勾）

- ☐ 提示「核销成功，快件已交付」
- ☐ 该件状态变为「已取件」
- ☐ 「在库快件」由 17 **变回 16**
- ☐ **同一货位的「已用数」比第 1 步少 1，剩余数多 1**
- ☐ 该件出现在货位详情里的快件列表中已消失
- ☐ 「快件查询 → 该件详情 → 轨迹」有两条记录：入库登记、取件核销

### 再验一条反例（AC-13-2）

用同一个取件码再核销一次 → 预期提示「该快件当前状态为「已取件」，不可取件」，
且货位数字**不再变化**（说明没有重复释放货位）。

**答辩话术**：*"核销时状态更新和货位释放放在同一个事务里，不会出现'状态改了但货位没放'。另外全系统对'货位是否占用'只有一个判断方法——以快件实体是否还在架上为准，在库、派送中、异常件算占用，已取件、已退回不算。取件、删除、异常退回、货位重算都复用这一个判断，所以不会出现各处口径不一致。"*

> 这也是我能给出"货位一致性"这条验收标准的原因——**这条是答辩最容易得分、也最容易被追问的点**。

## 四、实例 3：逾期保管费 + 四处数字一致（AC-14-1、AC-14-4）

当前有 **3 件**逾期未取快件（免费保管 3 天，逾期 2 元/天）：

> 想恢复成基线数字，重跑 `sql/01_schema.sql` + `sql/02_data.sql` 即可。

| 运单号 | 取件码 | 逾期天数 | 应缴 | 驿站 |
| ------ | ------ | -------- | ---- | ---- |
| `JT5566778899001` | `10045678` | 4 天 | **8.00 元** | 幸福小区 |
| `YD1122334455700` | `20033456` | 3 天 | **6.00 元** | 大学城 |
| `EMS8899001122334` | `10042319` | 2 天 | **4.00 元** | 幸福小区 |

| 4 | 在「取件核销」里输入 `10045678` 回车，看费用提示 | 取件核销页 |

### 预期结果

- ☐ 首页「逾期件」= **4**
- ☐ 逾期催取页统计卡 = **4**，列表也正好 **4** 条

## 五、实例 4：跨驿站越权拦截（AC-05-4）
### ⭐ 这个最能体现"安全意识"

**验收目的**：证明数据权限在后端强制收敛，改 URL 参数也偷不到别的驿站数据。

### 前置条件
两驿站数据量：幸福小区快递驿站（id=1）**15** 件、大学城菜鸟驿站（id=2）**10** 件，合计 **25** 件。

### 操作步骤

| 步 | 操作 | 位置 |
| -- | ---- | ---- |
| 1 | 退出，用 `staff01 / 123456` 登录（属于驿站 1） | 登录页 |
| 2 | 记下「快件查询」列表里的总条数 | 快件查询页 |
| 3 | 在浏览器地址栏把当前地址后面加上 `&stationId=2` 回车 | 地址栏 |
| 4 | 看列表条数与「所属驿站」列 | 快件查询页 |
| 5 | 地址栏访问 `http://localhost:5173/system/user` | 地址栏 |

### 预期结果

- ☐ 第 2 步：staff01 能看到 **15** 条，全部属于「幸福小区快递驿站」
- ☐ 第 4 步：**仍然是 15 条**，仍然全是「幸福小区快递驿站」——伪造 `stationId=2` **没有任何效果**
- ☐ 第 5 步：跳到 **403 页面**（或提示「无访问权限」），进不去用户管理
- ☐ 员工侧边栏**没有**「系统管理」这个一级菜单

### 对照实验（让导师看差异）

用 `admin` 登录同样加 `&stationId=2` → 只返回 **10** 条，全部属于「大学城菜鸟驿站」。
**管理员能筛驿站，员工不能越站**，这就是 RBAC + 数据权限的作用。

**答辩话术**：*"权限分两层：一层是功能权限，用注解加 AOP 切面拦接口，员工调用户管理接口直接返回 403；另一层是数据权限，在服务层强制把查询范围覆盖成本人所属驿站——注意是'覆盖'不是'兜底'，前端传什么都盖掉，所以改 URL 参数偷不到别的驿站数据。这个漏洞我开发中真实出现过一次，是员工显式传 stationId 就能查他站数据，后来补了越权测试才发现并修掉的。"*

### 预期结果

- ☐ 不登录也能打开这个页面（无侧边栏、深色背景）
- ☐ 输入 `13900000001` 返回 **1** 条，取件码 **`10012034`**，运单号 `SF1234567890123`，货位 `A-01-01`，驿站「幸福小区快递驿站」

## 七、实例 6：派送中当面签收（AC-16-1、AC-13-4）

**验收目的**：证明"在库 → 派送中 → 已取件"状态流转完整，且**派送中的件也能核销**
（这是开发中修过的一个真实缺陷：后端允许两种状态核销，前端只放行了在库）。

### 前置条件
现有一件**派送中**的快件：

| 运单号 | 取件码 | 收件人 | 货位 | 驿站 |
| ------ | ------ | ------ | ---- | ---- |
| `YD1122334455670` | `10073456` | 王磊 | `C-01-01` | 幸福小区快递驿站 |

### 操作步骤

| 步 | 操作 | 位置 |
| -- | ---- | ---- |
| 1 | 状态筛「派送中」，确认能看到 `YD1122334455670` | 快件查询页 |
| 2 | 去「货位地图」看 `C-01-01` 的已用数（派送中仍占货位） | 货位地图 |
| 3 | 进「取件核销」，输入 `10073456` 回车 | 取件核销页 |
| 4 | 取件方式选「送货上门」，核验方式选「身份证核验」→ 确认核销 | 核销表单 |
| 5 | 回「货位地图」再看 `C-01-01` | 货位地图 |

### 预期结果

- ☐ 第 1 步：派送中的件能被查到，状态显示「派送中」
- ☐ 派送中的件**允许核销**（若提示"状态不允许"，说明前端拦截了，是缺陷）
- ☐ 核销成功，提示「核销成功，快件已交付」
- ☐ `C-01-01` 已用数**减 1**（证明派送中也占用货位，核销后才释放）
- ☐ 该件轨迹里出现「派送」「取件核销」两条记录

**答辩话术**：*"状态机是在库 → 派送中 → 已取件。派送中件还在驿站，所以货位仍算占用；只有核销才释放。这里开发时踩过一个坑：后端允许在库和派送中都能核销，前端只放行了在库，导致送货上门当面签收时点不了核销，件会永远挂在派送中。后来前后端统一了口径。"*

## 九、实例 8：异常件退回后释放货位（AC-19-1、AC-20-3）
### ⭐ 货位一致性的第二次验证

**验收目的**：证明异常件"占用货位"，而处理成"已退回"后**必须释放货位**。
（这正是开发中修复的库存不一致缺陷）

### 前置条件
- 一件在库快件：`JD9988776655441`，取件码 `10023451`，货位 `A-01-02`
- 当前异常件 **3** 条：1 条「待处理」、1 条「处理中」、1 条「已解决」
- 货位占用合计 **19** 件（货位地图顶部「在架快件」）

> **处理状态只有三种：待处理 / 处理中 / 已解决**（注意不是"已完成"）。
> 处理对话框里有三个字段：**处理状态**（下拉）、**处理结果**（文本）、
> **同步快件状态**（下拉，选了会同时改快件状态，留空则不改）。

### 操作步骤

| 步 | 操作 | 位置 |
| -- | ---- | ---- |
| 1 | 先去「货位地图」记下 `A-01-02` 的已用数 | 货位地图 |
| 2 | 「异常件管理 → 登记异常」，运单号填 `JD9988776655441`，异常类型选「破损」，提交 | 异常件管理 |
| 3 | 再回「货位地图」看 `A-01-02` | 货位地图 |
| 4 | 「快件查询」看该件状态 | 快件查询 |
| 5 | 「异常件管理」找到该条 → 点「处理异常」→ **处理状态选「已解决」**、处理结果填文字、**同步快件状态选「已退回」** → 确认处理 | 异常件管理 |
| 6 | **再回「货位地图」看 `A-01-02`** | 货位地图 |

### 预期结果

- ☐ 第 3 步：`A-01-02` 已用数**不变**（异常件仍占货位，东西还在驿站）
- ☐ 第 4 步：快件状态变为「**异常件**」
- ☐ 异常件列表由 3 条变 **4** 条
- ☐ 第 5 步：提示「异常处理完成」，该条处理状态变「**已解决**」
- ☐ 第 6 步：`A-01-02` 已用数**减 1**，货位地图顶部「在架快件」也**减 1**
- ☐ 该件状态变为「**已退回**」，货位显示为空，轨迹里出现异常登记与处理记录

**答辩话术**：*"这里最容易出错。异常件在驿站里躺着，货位当然还被占着；一旦退回，件离开驿站，货位必须释放。我统一了'快件实体是否还在架上'这一个判断，在库、派送中、异常件算占用，已取件、已退回不算。取件、删除、异常退回、货位重算全部复用这一个判断，另外提供一键重算接口修复历史数据。"*

## 十、实例 9：导出台账 Excel（AC-23-1、AC-23-2）

**验收目的**：证明导出按当前筛选条件走，不是把全库都导出去。

### 操作步骤

| 步 | 操作 |
| -- | ---- |
| 1 | 「快件查询」，状态筛「**在库待取**」，记下总条数 |
| 2 | 点「导出」→ 下载 xlsx |
| 3 | 用 Excel 打开，数行数 |
| 4 | 回到页面，再加一个条件（如快递公司选「顺丰速运」），再导出一次 |

### 预期结果

- ☐ 第 1 步：在库件 **16** 条
- ☐ 第 3 步：Excel 有 **1 行表头 + 16 行数据**
- ☐ 表头与页面列一致（运单号、取件码、收件人、手机号、公司、状态…）
- ☐ 中文表头**不乱码**，日期与金额格式正常
- ☐ 第 4 步：加上第二个条件后导出的条数**变少**（证明带筛选条件）

**答辩话术**：*"导出走的是和列表查询同一套条件构造，所以筛什么就导什么，不会把别的驿站或别的状态的件带出去——导出接口同样受数据权限约束。"*

## 十一、实例 10：角色权限变更即时生效（AC-05-2）

**验收目的**：证明权限是"配置"出来的，改完不用改代码、重新登录就生效。

### 前置条件
- `STAFF` 角色当前有 **29** 项权限
- 权限树共 **43** 项

### 操作步骤

| 步 | 操作 |
| -- | ---- |
| 1 | 「系统管理 → 角色权限」，选中「驿站员工」 |
| 2 | 看权限树勾选数量（应 29 项） |
| 3 | 取消勾选「通知记录」相关权限 → 保存 |
| 4 | **退出登录，用 `staff01 / 123456` 重新登录** |
| 5 | 看侧边栏 |
| 6 | 用 `admin` 登回去，把权限勾回来，保存 |

### 预期结果

- ☐ 第 2 步：权限树按菜单/按钮两级展示，共 43 项，员工角色默认勾选 29 项
- ☐ 第 5 步：侧边栏的「**通知管理**」**消失**（菜单按权限渲染）
- ☐ 若直接在地址栏访问该页 → 跳 **403** 或提示无权限
- ☐ 恢复权限后重新登录，菜单**回来**

**答辩话术**：*"菜单和按钮都是按权限动态渲染的，权限改了重新登录就生效，不用发版。后端还有一层注解加切面的接口鉴权——所以就算手动敲地址、或者直接调接口，没有权限照样是 403。"*

## 十二、实例 11：普通用户只能看自己的件（AC-10-4）

**验收目的**：证明普通用户的数据范围是按手机号收敛的，不是按驿站。

### 前置条件
`user01` 的手机号是 `13900000001`，名下只有 **1** 件在库快件。

### 操作步骤

| 步 | 操作 |
| -- | ---- |
| 1 | 用 `user01 / 123456` 登录 |
| 2 | 看侧边栏菜单数量 |
| 3 | 「快件查询」看总条数与每一行的收件人手机号 |
| 4 | 地址栏在地址后加 `&stationId=1` 回车 |

### 预期结果

- ☐ 侧边栏只有 **3** 项（首页概览、个人中心、快件查询），没有系统管理/通知/货位地图等
- ☐ 快件查询总共 **1** 条
- ☐ 这一条的收件人手机号是 `13900000001`（就是他自己）
- ☐ 加 `&stationId=1` 后**仍是 1 条**（伪造参数无效）
- ☐ 看不到其他任何人的快件

**答辩话术**：*"三类角色的数据范围完全不同：管理员看全部驿站；员工看本驿站全部件；普通用户只看自己手机号名下的件。这三种范围都在服务层强制施加，前端传什么参数都不改变结果。"*
